Fluxo de Estágios do Projeto

Padroniza os status utilizados no Zoho Sprints para acompanhar uma demanda desde a entrada até a entrega em produção — o que cada estágio significa, quando mover um item entre eles e como tratar os casos de impedimento e cancelamento.

Seção 01

Visão geral do fluxo

Este é o fluxo recomendado para acompanhar qualquer item — demanda, história ou tarefa — desde a liberação da oportunidade até a publicação em produção. A sequência abaixo representa o caminho feliz, ou seja, o percurso de um item que avança sem impedimentos.

Business→ Backlog→ Ready for Dev→ In Dev→ Ready for QA→ In QA→ Homologação→ Done
⚠ Blocked e Canceled não são etapas sequenciaisBlocked e Canceled não fazem parte da linha reta acima. São estados de exceção que podem ocorrer a partir de praticamente qualquer etapa ativa do fluxo — por isso são tratados separadamente nas Seções 05 e 06, e não como um passo fixo entre dois outros.

Depois da aprovação do cliente em Homologação e da publicação em produção, o item vai direto para Done. Future Milestones não faz parte desta linha principal — pedidos novos, fora do escopo contratado, seguem um caminho próprio, descrito na Seção 03.

Seção 02

O que significa cada estágio

Use esta referência para decidir em qual status um item deve estar. Cada linha descreve o objetivo do estágio e o critério prático para utilizá-lo.

StatusObjetivoQuando utilizar
BusinessEntrada e preparação da demandaA oportunidade foi liberada para criação do projeto e está passando pela alocação inicial, definição de equipe e preparação do projeto. Business não representa desenvolvimento.
BacklogFila de demandasItem registrado e, eventualmente, priorizado — mas ainda não selecionado para uma Sprint. Não deve ser considerado trabalho em andamento.
Ready for DevPronto para desenvolvimentoItem retirado do Backlog, priorizado para a Sprint e com informações suficientes para iniciar o desenvolvimento: requisito definido, responsável atribuído, critérios de aceite disponíveis.
In DevDesenvolvimento ativoItem que está efetivamente sendo desenvolvido pelo time. Só deve ser usado quando o trabalho tiver sido de fato iniciado.
BlockedImpedimentoItem cujo andamento está impedido por uma dependência real, problema técnico ou informação pendente. Assim que o impedimento for resolvido, retorna automaticamente ao estágio em que estava. Detalhes na Seção 05.
Ready for QAAguardando testesDesenvolvimento concluído, critérios de aceite atendidos e item disponibilizado para o time de QA iniciar os testes. Não deve ser considerado desenvolvimento ativo.
In QATestesItem sendo testado pelo QA: testes funcionais, validação de requisitos, testes de integração e identificação de eventuais bugs.
HomologaçãoValidação do clienteItem aprovado pelo QA e disponibilizado para o cliente validar o comportamento esperado. Eventuais ajustes solicitados pelo cliente devem ser registrados.
DoneFinalizadoEntrega aprovada pelo cliente na homologação e publicada em produção, com critérios de conclusão atendidos e sem pendência impeditiva relacionada à entrega.
CanceledCanceladoItem que não será mais executado, a partir de qualquer etapa. Deve registrar, sempre que possível, o motivo do cancelamento.

Seção 03

Demandas futuras (Future Milestones)

O conceito de Future Milestones foi mantido, mas deixou de ser tratado como uma etapa normal da Sprint. Ele existe para separar pedidos novos — fora do escopo já contratado — das demandas que já estão priorizadas no Backlog, evitando que as duas coisas se misturem.

Novo pedido→ Future Milestone→ Avaliação comercial→ Novo contrato/escopo→ Backlog→ Sprint
ℹ Quando usarUse Future Milestone para registrar novos pedidos, novas necessidades ou novos escopos identificados durante o projeto, mas que não fazem parte do contrato atual. O item só entra no Backlog — e, portanto, na fila de execução — depois que a avaliação comercial resultar em um novo contrato ou escopo aprovado.

Seção 04

Regras de transição

Para manter o board confiável, cada mudança de status deve obedecer a um critério objetivo. Estas são as regras do caminho principal — os impedimentos estão detalhados na Seção 05 e as revisões/cancelamento na Seção 06.

  1. Business → Backlog

    Projeto pronto para priorização

    • Projeto criado.
    • Alocação inicial realizada.
    • Demanda pronta para ser priorizada.
  2. Backlog → Ready for Dev

    Demanda priorizada para a Sprint

    • Demanda priorizada.
    • Incluída na Sprint.
    • Requisitos suficientemente definidos.
    • Responsável definido.
  3. Ready for Dev → In Dev

    Desenvolvimento iniciado

    • Desenvolvedor iniciou efetivamente o trabalho.
  4. In Dev → Ready for QA

    Pronto para testes

    • Desenvolvimento concluído.
    • Critérios de aceite atendidos.
    • Evidências/informações necessárias para o QA disponíveis.
  5. Ready for QA → In QA

    Testes iniciados

    • QA iniciou os testes.
  6. In QA → Homologação

    Aprovado pelo QA

    • Testes concluídos.
    • Sem pendências impeditivas.
    • QA aprovou a entrega.
  7. Homologação → Done

    Aprovado pelo cliente e publicado

    • Cliente aprovou a entrega.
    • Publicação realizada em produção.
    • Entrega concluída.

Seção 05

Impedimentos (Blocked)

Blocked não é uma etapa obrigatória do fluxo — é um estado temporário e excepcional, usado apenas quando existe um impedimento real que impede a continuidade do trabalho.

O que é — e o que não é — um impedimento

Motivo válido para bloquear

Existe um impedimento real

  • Dependência externa.
  • Falta de informação.
  • Problema técnico.
  • Dependência do cliente.
  • Dependência de outra equipe.
  • Aprovação pendente.
  • Indisponibilidade de ambiente.
  • Dependência de outra tarefa/projeto.
≠
Não é motivo para bloquear

Isso não é um impedimento

  • A tarefa simplesmente está atrasada.
  • O responsável ainda não iniciou o trabalho.
  • A tarefa perdeu prioridade.
  • O responsável está ocupado com outra coisa.
  • A tarefa está parada sem impedimento identificado.

Retorno automático ao estágio de origem

Ao mover um item para Blocked, o sistema registra qual era o status válido imediatamente anterior ao bloqueio. Quando o impedimento é resolvido, o item retorna automaticamente para esse status — não necessariamente para In Dev.

Entrada

Qualquer etapa → Blocked

Exemplos: In Dev → Blocked, Ready for QA → Blocked, In QA → Blocked e Homologação → Blocked.

⇄
Retorno

Blocked → status de origem

O impedimento foi solucionado e o item retoma exatamente de onde estava — a mesma etapa registrada no momento do bloqueio.

ℹ Motivo e categoria são obrigatóriosTodo bloqueio precisa de um motivo descrito e, quando disponível, de uma categoria: Dependência do Cliente, Dependência Interna, Dependência Externa, Problema Técnico, Falta de Informação, Aprovação, Ambiente ou Outro. Da mesma forma, o desbloqueio deve registrar uma observação sobre como o impedimento foi resolvido.

Múltiplos bloqueios na mesma tarefa

Uma mesma tarefa pode ser bloqueada mais de uma vez ao longo do seu ciclo de vida. Cada bloqueio é um registro independente — início, status de origem, motivo, resolução e duração — e nenhum histórico anterior é sobrescrito. Isso permite saber quantas vezes um item foi bloqueado, por quais motivos e por quanto tempo, no total.

Como o tempo bloqueado entra nos indicadores

⚠ Não é atraso do responsávelO tempo em que um item permanece em Blocked é contado separadamente e não é atribuído automaticamente como atraso do responsável. Os indicadores da Central de Gestão devem diferenciar tempo de execução, de QA, de homologação, de bloqueio e o tempo total da tarefa — e permitir análises como quantidade de bloqueios, tempo médio e total bloqueado, motivos mais frequentes e os projetos com maior incidência.

Seção 06

Revisões e cancelamento

Além dos impedimentos, o fluxo prevê dois outros desvios do caminho principal: o retorno de um item para correção quando um problema é encontrado depois do desenvolvimento, e o cancelamento definitivo de uma demanda.

Problemas encontrados no QA

Problema encontrado

In QA → In Dev

O QA identificou bugs ou não conformidades que exigem nova correção de desenvolvimento.

→
Depois da correção

In Dev → Ready for QA → In QA

Corrigido o problema, o item refaz o caminho normal até ser testado novamente pelo QA.

Reprovação na homologação

Cliente reprovou

Homologação → In Dev

O cliente solicitou correção durante a homologação e o item retorna para desenvolvimento.

→
Depois da correção

In Dev → Ready for QA → In QA → Homologação

O item refaz todo o caminho — incluindo o QA — antes de voltar à validação do cliente.

Canceled pode vir de qualquer etapa

⛔ Não é um destino sequencialUm item pode ser cancelado a partir de praticamente qualquer etapa — inclusive direto do Backlog ou do Business, sem nunca ter entrado em desenvolvimento. Ao mover um item para Canceled, registre sempre que possível o motivo do cancelamento nos comentários; isso preserva o histórico e evita retrabalho de investigação no futuro.

Seção 07

Boas práticas de governança

✓

Blocked e Canceled são estados de exceção, não etapas do board: trate-os como uma marcação temporária ou definitiva, nunca como um passo obrigatório entre dois outros estágios.

✓

Done só depois da publicação: a entrega é considerada concluída apenas quando já foi aprovada pelo cliente e efetivamente publicada em produção.

✓

Todo bloqueio e todo cancelamento registram o motivo: um comentário curto no momento certo evita retrabalho de investigação semanas depois.

✓

Mova o item no mesmo dia em que o status muda de fato: um board atualizado em tempo real é o que permite relatórios de prazo, bloqueio e capacidade confiáveis.
